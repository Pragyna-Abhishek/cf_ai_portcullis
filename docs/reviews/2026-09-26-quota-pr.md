# Review response: PR #4 (Workers AI quota handling)

An independent review of this PR found four issues. This document covers each one: what was
wrong, how it was verified, how it was fixed, and the result of checking the fix against a
mutation of the code it covers.

## 1. The "never retried" test did not test the real code

**Finding.** `test/integration/failure-injection.test.ts` had a test named "a draft-rule call that
fails with a quota-exhausted-shaped error fails the incident immediately". It used
`mockStepError` to make the `draft-rule-attempt-1` step throw a pre-written error message
directly. `mockStepError` replaces the step's body outright, so the test never ran the step's real
code, including the `try { requireOkResponse(response) } catch (e) { if (e instanceof
QuotaExhaustedError) throw new NonRetryableError(e.message) }` block in
`src/server/workflow.ts` that is the actual fix for "a 3036 error is never retried". The test
would pass identically whether that block existed or not.

**How it was verified.** Removed the `NonRetryableError` wrapping from `workflow.ts` (kept only
the bare `requireOkResponse(response)` call) and re-ran the old test. It still passed, confirming
it could not catch this regression.

**Fix.** Replaced the test with one that runs the real (unmocked) `draft-rule-attempt-1` step body
against a scripted AI binding. Since integration tests normally run with `MODEL_MODE=fake`
(a canned model, not the real Workers AI client), the test temporarily swaps `env.MODEL_MODE` to
`"workers-ai"` and `env.AI` to a script for the one test, restoring both in a `finally` block. The
script returns canned "ok" responses for the classify-symptom and hypothesize calls (identified by
comparing `inputs.response_format.json_schema` against the imported `CLASSIFY_JSON_SCHEMA` /
`HYPOTHESIZE_JSON_SCHEMA` objects by reference) and throws a `"3036: daily allocation used up"`
error only for the draft-rule call (identified the same way, against `RULE_JSON_SCHEMA`). The test
counts how many times that draft-rule branch is invoked and asserts it is exactly 1.

**Proof.**
- With the `NonRetryableError` wrapping removed: the test failed with `expected 3 to be 1` (the
  step's own retry policy, `{ retries: { limit: 2, ... } }`, ran the call three times before the
  Workflow gave up).
- With the wrapping restored: the test passed, `draftCalls` was 1, and `done.failureReason`
  matched `/model call failed \(quota-exhausted\): 3036/`.

New test: `test/integration/failure-injection.test.ts`, describe block "failure injection: model
quota exhaustion (CLAUDE.md: never retried, at any level)".

## 2. The quota flag never cleared at the daily reset

**Finding.** `recordModelOutcome` set `SETTING_MODEL_QUOTA_EXHAUSTED_AT` to a timestamp the moment
a real model call returned `quota-exhausted`, and only cleared it when a later real call returned
`ok`. Workers AI's daily free allocation resets at 00:00 UTC regardless of whether the account
happens to make another model call that day. If no real call was ever attempted again (for
example, if the operator stopped starting new investigations for a day), the UI would keep
showing "model unavailable: daily quota used" indefinitely, past the point where the account could
actually serve a request again.

**Fix.** `modelStatus()` in `src/server/agent.ts` now compares the UTC calendar day the flag was
set on against the UTC calendar day of "now" (`utcDayKey`, a `YYYY-M-D` string from `getUTCFullYear
`/`getUTCMonth`/`getUTCDate`). If the stored timestamp is from an earlier UTC day, the status reads
"live" even though the flag setting itself was never cleared. `recordModelOutcome` still clears
the flag outright on a successful call, same as before; the day check is a second, independent way
the same status can become "live" again.

Because this needed a specific point in time to test against, and the code must not read the wall
clock inside a Workflow step (CLAUDE.md invariant 12) or a test, `IncidentAgent` gained a
test-only injectable clock: `setClockForTest(fixedMs: number | null)`, read by a private `now()`
that falls back to `Date.now()` when no override is set. `recordModelOutcome` now stamps the flag
using `this.now()` instead of `Date.now()` directly, so the same override drives both the write
and the read side of the comparison in tests.

## 3. No tests for modelStatus / recordModelOutcome at all

**Finding.** Neither `modelStatus()` nor `recordModelOutcome()` had a dedicated test. The existing
end-to-end Workflow tests only exercised the "fake" branch (the fake model never returns
quota-exhausted).

**Fix.** New file `test/integration/model-status.test.ts`, five tests:
- `"fake"` regardless of any recorded outcome, when `MODEL_MODE` is fake.
- `"live"` when `MODEL_MODE` is not fake and nothing has been recorded.
- becomes `"quota-exhausted"` the moment a quota-exhausted response is recorded.
- clears back to `"live"` the moment a later `ok` response is recorded, same UTC day.
- expires back to `"live"` once the UTC day it was set on has passed, with no later `ok` response
  needed (using `setClockForTest`, never real time).

These tests call `recordModelOutcome` and read `modelStatus` through `agent.state` directly by
Durable Object RPC, without running a full Workflow, since neither method reads or writes anything
a Workflow step produces. `MODEL_MODE` and `AI` are swapped the same way as in the fix for finding
1 (an Agent's `env` is bound once, when its Durable Object is first constructed, so both the agent
name and its first RPC call have to happen inside the override, not before it. An early mistake
in writing these tests: an agent built under "fake" mode kept reporting "fake" even after
`MODEL_MODE` was flipped back for the assertion, which is what led to catching this).

Writing these tests also surfaced a second, smaller bug: `recordModelOutcome`'s quota-exhausted
branch, and its ok-with-no-usage branch, updated the stored setting but never called
`this.refreshState()`, so the change was invisible in `agent.state` until something unrelated
happened to refresh it (in production, the calling Workflow step's own `recordStep` call papered
over this every time, which is why it was never noticed). Both branches now call
`refreshState()` themselves. A `refreshStateForTest()` method was also added, used by the "expires"
test to force a state recompute after moving the injected clock forward with no other event to
trigger it (mirroring what "the next step, or a browser action" would do in production the moment
the UTC day rolls over).

**Proof, one case as an example (day-boundary logic, finding 2's fix).** Reverted `modelStatus()`
to the old two-branch version (`this.env.MODEL_MODE === "fake" ? "fake" : (flag ? "quota-exhausted"
: "live")`, no day comparison) and re-ran `model-status.test.ts`. The "expires back to 'live'"
test failed: `expected 'quota-exhausted' to be 'live'`. Restored the fix; all 5 tests passed.

## 4. Inaccurate comment about which error codes are documented

**Finding.** The comment above `classifyError` in `src/model/workers-ai.ts` said "3036 and 4006
are both documented as ... Codes from workers-ai/platform/errors.mdx." Cloudflare's errors page
documents 3036 (and 3040) for Workers AI; it does not list 4006. 4006 is a code this account
observed directly (recorded in `docs/spikes.md` and `docs/eval-results/README.md`), not one found
in Cloudflare's own documentation.

**Fix.** Reworded the comment to say exactly that: 3036 is Cloudflare's documented code, 4006 is
what this account observed for the same condition and is treated the same way, and 429/3040 are
the documented transient codes handled separately.

- `npm run test:integration` (`vitest run --config vitest.integration.config.ts --max-workers=1
  --no-isolate`): 46 tests passed, 5 files (including the two new/changed files above).
- Mutation checks: for finding 1, removing the `NonRetryableError` wrapping turned the new test
  red (3 calls instead of 1); for finding 2/3, removing the UTC-day comparison in `modelStatus()`
  turned the new "expires" test red. Both were restored and re-verified green.

Nothing else was changed. No new dependency, no new Durable Object, no schema change beyond what
the PR already introduced.
